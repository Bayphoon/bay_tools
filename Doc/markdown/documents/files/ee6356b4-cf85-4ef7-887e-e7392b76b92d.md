## 主 agent 与 subagent 工作流

### 通用职责

- 主 agent 负责需求分析、代码调查、方案设计、任务委派和最终验收。
- 涉及代码修改的任务，原则上由 worker subagent 实施，主 agent 负责协调和审查。
- 只读分析、解释、代码审查或问题诊断任务，可以由主 agent 直接完成，并按需启动 explorer subagent。
- 除非多个任务可以完全独立完成，否则不得让多个 subagent 并行编辑代码。

### 计划模式

- 主 agent 负责需求分析、代码调查和方案设计。
- 可以启动 explorer subagent，对相互独立的问题进行只读调查。
- 不得启动执行型 worker 修改代码。
- 不得实施代码修改。
- 主 agent 必须汇总调查结果，输出包含以下内容的方案：
  - 涉及文件和代码范围
  - 分步骤实施内容
  - 预期行为变化
  - 潜在风险
  - 验证方法
- 方案输出后等待用户确认。
- 用户明确确认方案或在 Codex App 中点击“执行方案”，均视为方案已确认。

### 普通模式

- 普通模式默认是连续执行模式，不需要用户确认方案。
- 收到需求后，主 agent 必须先检查实际代码并形成工作方案。
- 主 agent 可以向用户简要说明方案或执行进度，但不得默认停下来等待方案确认。
- 如果当前上下文包含从计划模式确认的方案，应直接使用该方案，不得重新规划或再次要求确认。
- 对于需要修改代码的任务，中等及以上代码修改由 worker 实施；极小修改、紧急修正或无法独立拆分的修改可由主 agent 直接处理
- 主 agent 应向 worker 提供：
  - 明确的任务目标
  - 涉及范围
  - 实施步骤
  - 必须遵守的约束
  - 验收标准
- worker 可以在需求和方案范围内自行处理实现细节，不需要逐项请求确认。
- worker 不得自行扩大需求或修改与任务无关的代码。
- worker 遇到问题时，应先向主 agent 报告。
- 主 agent 应优先通过补充指令让同一个 worker 继续处理，不得因为普通实现细节而中断任务询问用户。
- 只有出现以下情况时才向用户请求确认：
  - 缺少会显著影响最终行为的必要选择
  - 需要扩大到原需求之外的功能或文件范围
  - 需要执行破坏性或不可恢复操作
  - 需要新的权限、账号或外部系统授权
  - 不同处理方向会产生明显不同的产品行为
- worker 完成后，主 agent负责：
  - 审查实际 diff
  - 检查是否满足原始需求
  - 检查是否遗漏或偏离方案
  - 检查是否修改了无关文件
  - 执行允许范围内的验证
- 如果审查发现方案范围内的问题，主 agent 应向同一个 worker 发送修正要求。
- worker 修正完成后，主 agent 应再次审查。
- 主 agent 应在实现和审查完成后直接向用户提交最终结果，不再要求额外确认。


## Subagent 模型和推理强度

- 主 agent 使用当前会话选择的模型和推理强度，负责分析、规划、协调和验收。
- explorer subagent 默认继承主 agent 的模型和推理强度，除非另有配置。
- worker subagent 使用：
  - 模型：`gpt-5.6-luna`
  - 推理强度：`medium`
- 启动 worker 时，主 agent 必须显式指定上述模型和推理强度。
- worker 必须严格按照主 agent 提供的方案和原始需求修改代码。
- 如果指定模型当前不可用，主 agent 可以使用可用的执行模型继续任务，但必须在最终结果中说明实际使用的模型。

## 验证和文件约束

- Lua 代码无需进行编译级验证。
- C# 代码无需重新编译。
- 除非用户明确要求，不启动 Unity Editor，不执行 Unity 构建，也不进行 Unity 内运行时验证。
- 默认通过代码审查、调用点检查、diff 检查和其他不会触发 Unity 编译的方式进行验证。
- 最终结果必须明确说明哪些验证已完成、哪些编译或运行时验证未执行。
- 未经用户针对具体文件的明确授权，不得删除 Git 工作区中的任何文件。
